The 'global' mess

Here's the pattern from a real game in our class. The player's stuff is scattered as separate global variables, and every function has to declare global to touch them:

❌ Player data scattered as globals
coins = 0 inventory = [] health = 100 def buy_sword(): global coins, inventory # need this in EVERY function coins = coins - 10 inventory.append("sword") def take_damage(amount): global health health = health - amount

Problems: the player's data is in 3 separate places; every function needs global; and if you want a SECOND player, you'd have to copy every variable (coins2, health2...). Messy and doesn't scale.

Fix — put related data in ONE box (a class)

A class is a blueprint for an object that holds related data together. Here, all the player's stuff lives inside one Player:

✅ One Player object holds it all
class Player: def __init__(self): self.coins = 0 self.inventory = [] self.health = 100 def buy_sword(self): self.coins -= 10 self.inventory.append("sword") def take_damage(self, amount): self.health -= amount # make a player and use it: hero = Player() hero.buy_sword() hero.take_damage(20) print(hero.health) # 80

What just happened?

  • class Player: — the blueprint (the cookie cutter).
  • __init__ — the setup method that runs when you make a player. It puts the starting data ON the object.
  • self.coins — 'this particular player's coins'. No more global.
  • hero = Player() — builds one actual player (an 'instance') from the blueprint.
  • Want a second player? villain = Player(). Done. Each has its own coins, health, inventory.

self is the magic word

self means 'the object this method was called on'. hero.take_damage(20) sends hero in as self, so self.health -= 20 changes hero's health. Call it on villain and it changes villain's. Same method, different object — no globals needed.
