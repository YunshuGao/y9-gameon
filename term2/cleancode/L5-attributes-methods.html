Attributes (HAS) vs Methods (DOES)

Think of an object as a noun. Its attributes are adjectives (what it HAS); its methods are verbs (what it DOES).

class Pet: def __init__(self, name): self.name = name # ATTRIBUTE — what the pet HAS self.hunger = 50 # ATTRIBUTE def feed(self): # METHOD — what the pet DOES self.hunger = self.hunger + 10

Passing values IN through __init__

In Lesson 4 every player started the same. But real objects differ — this pet's NAME comes in as a parameter when you build it:

✅ Each object built with its own values
class Pet: def __init__(self, name, species): self.name = name self.species = species self.hunger = 50 mochi = Pet("Mochi", "dog") felix = Pet("Felix", "cat") print(mochi.name) # Mochi print(felix.species) # cat

Pet("Mochi", "dog") sends "Mochi" in as name and "dog" in as species. __init__ stores them on self. Two pets, different data, same blueprint.

The real trick from our class — clamping a stat

A pet game in our class needed hunger to stay between 0 and 100, no matter how much you feed. Feeding past 100 should cap at 100. Here's the clean way, using min():

✅ min() caps the top, max() caps the bottom
def feed(self): self.hunger = min(100, self.hunger + 10) # never goes above 100 def pass_time(self): self.hunger = max(0, self.hunger - 5) # never goes below 0

min(100, x) = 'the smaller of 100 and x' → can't exceed 100. max(0, x) = 'the bigger of 0 and x' → can't go below 0. Two tiny functions that replace clunky if-statements.

Methods can take parameters too

A method isn't limited to self — it can take more inputs:

def feed(self, amount): self.hunger = min(100, self.hunger + amount) mochi.feed(25) # feed 25, not the fixed 10
